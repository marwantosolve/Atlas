# Atlas v1 — From Here to Public

> **Purpose.** This is the working plan that takes Atlas from its current state
> (Phases 0–1 complete) to a **v1 that can be made public**: a repo someone can
> clone, install, run, and see do its basic job — reconstruct a run into an
> execution graph, localize a failure, and show its blast radius — through a CLI,
> an HTTP API, and a minimal web UI, with an optional natural-language `ask`
> command on top.
>
> Scope decisions in this document were confirmed with the project owner on
> 2026-08-29: **v1 interface = CLI + HTTP API + web UI**, and the **LLM layer
> ships as a thin, optional, key-gated layer in v1** (deterministic engine stays
> the source of truth — ADR-002 / plan §22.2).
>
> `ATLAS_IMPLEMENTATION_PLAN.md` remains the strategic reference; where the two
> disagree, `docs/decisions.md` and this file are current.

## 1. Where we are

| Done | Evidence |
|---|---|
| Phase 0 — domain models | `src/atlas/models/` (Node, Run, Edge, Failure, registries, enums), `docs/event-schema.md` |

Nothing analytical exists yet: no graph, no retry detection, no propagation, no
root cause, no API, no UI.

## 2. What v1 is — and is not

**v1 is** the deterministic core (Phases 2–5) plus the delivery surfaces
(Phase 6 store/API, Phase 7 CLI/UI) and the thin optional LLM layer.

**v1 is not** (deferred to v2+):

- the benchmark with ground-truth files (plan Phase 8 — the ground-truth format
  is still an open question in `docs/decisions.md`),
- cross-run structural comparison (ADR-002 item 4),
- LangGraph/CrewAI/AutoGen adapters (inherited from MASEF when needed),
- any LLM involvement in *analysis* (the LLM only queries and explains
  deterministic results),
- Neo4j, OTel collectors, auth, multi-tenancy (plan §20).

## 3. Definition of done

A clean clone of the public repo supports, with no access to any private
sibling repo:

```bash
uv sync --extra dev --extra api
uv run pytest                          # all green, no skips that matter
uv run atlas analyze examples/traces/refund_run.json     # text diagnosis
uv run atlas analyze examples/traces/refund_run.json --format json
uv run atlas serve --store ./runs      # API + UI on http://127.0.0.1:8000
uv run atlas ask "why did this run fail?" --run <id>     # only with an API key set
```

`atlas analyze` on the failing demo trace prints: run summary, the execution
graph, detected failures with evidence, propagation path, blast radius, root
cause, retry waste. `atlas serve`'s web UI shows the same: a run list, a run
detail with the graph rendered, and a diagnosis panel.

## 4. Milestones

Each milestone lands as one or more atomic commits with tests green at every
commit. Ordering is M0 → M6 strictly; M7 starts once M6's response schemas are
frozen and can run in parallel.

### M0 — baseline commits + the demo corpus *(no new code)*

The working tree holds Phases 0–1 **uncommitted**. Before building anything:

1. Commit the existing work in atomic commits (models+schema docs, ingestion,
   attribution, tests, project scaffolding) — history should read like the work
   happened stepwise.
2. Author `examples/traces/refund_run.json`: a synthetic MASEF-format trace of
   the canonical interview scenario — orchestrator → researcher (policy search,
   succeeds) ∥ CRM agent (tool fails, retries, fails again) → writer → final
   answer. Multi-agent, parallel branches, one tool failure with retry, ~20–30
   spans, valid against the same rules ingestion enforces.
3. Keep `examples/traces/minimal_run.json` (5-span success) as the smoke trace.
4. `prompt.txt` and `ATLAS.pdf` stay untracked (private conversation / spec
   doc — publishing decision is the owner's, at release time). Add both to
   `.gitignore`.

The refund trace is the acceptance fixture for M2–M5: every milestone's tests
assert against it, so it must exist before the graph code does.

### M1 — Phase 2: execution graph reconstruction

**Deliverable:** `src/atlas/graph/` — `build_execution_graph(run) -> ExecutionGraph`.

- NetworkX `DiGraph` (new dep, per ADR-005) keyed by span id; node attributes
  carry the `Node` model.
- Edge population, in order of strength:
  - `CALL` from `parent_id` (invocation nesting — always available at L1).
  - `HANDOFF` from `communication_graph.edges` with `traversed: true`, joined
    through agent attribution to the **agent-owning spans** (schema doc §4:
    the `CHAIN` span under the framework wrapper, else the `span_name`-resolved
    span — the duplicate-span quirk rule).
  - `RETRY` from `retry_of` — empty until M2 populates the field.
  - `DATA` stays **unpopulated in v1**. This is the ADR-009 decision, recorded
    here: cross-*agent* dataflow rides `HANDOFF` (the strongest of ADR-009's
    three signals — explicitly recorded, `traversed`-gated, agent-granular);
    span-level value matching and `langgraph_step` inference are deferred.
    ADR-009 is updated to record this choice and its coverage on the reference
    trace.
- Graph queries the later phases build on: `parents/children`, `descendants`,
  `ancestors`, `agents()` rollup (owning spans only), `subtree(node_id)`,
  `to_dot()` / pyvis export (for M6's UI).
- **Tests:** every plan §17 case against synthetic traces — simple success,
  tool failure, retry, multi-agent, parallel branches, partial failure — plus
  graph shape assertions on the refund trace (branch count, handoff edges,
  no cycles).

### M2 — Phase 3: retry detection and retry-waste attribution

**Deliverable:** `src/atlas/graph/retries.py` (or `analysis/` — whichever the
M1 package layout settled on).

- Retry rule (deterministic, evidence-first): spans *sibling under the same
  parent*, *same owning agent*, *same name or tool*, *non-overlapping time
  intervals*, where the earlier span's status is `ERROR` (or it has a
  status_message) → the later span is a retry of the earlier. The rule and its
  limits get documented in `docs/`; a span that matches nothing stays
  `attempt=1, retry_of=None` (schema rule 8: no guessing at ingestion).
- Detection produces a `RetryGroup` list (canonical attempt, retries, final
  outcome), and *then* the graph gains its `RETRY` edges.
- **Retry waste** — the only impact figure Atlas may claim (ADR-003): per group,
  the duration and *carried* `cost_usd` of superseded attempts; aggregated per
  agent and per run. Never a counterfactual "+X would have been saved".
- **Tests:** retry groups found on the refund trace (CRM attempt 1→2), no false
  retries on parallel same-tool branches (distinct parents/intervals), waste
  arithmetic pinned exactly.

### M3 — Phase 4: failure severity, propagation, blast radius

**Deliverable:** `src/atlas/analysis/failures.py`.

- Failure detection, two sources (ADR-008):
  - **Structural:** `ERROR_STATUS` (span status ERROR), `EXHAUSTED_RETRIES`
    (retry group whose final attempt failed), `MISSING_OUTPUT` (LLM/TOOL span
    with no output and no error — flagged as suspected, severity-capped).
  - **Seeded:** caller-supplied verdicts (`span_id → {kind, message}`), the
    MASEF cross-link join. Atlas localizes and propagates them; it never
    re-judges.
- Propagation relation per ADR-009, with edge provenance on every hop:
  - within an agent: descendants via `CALL` edges;
  - across agents: `HANDOFF` edges (traversed) — this is what catches
    "writer consumed the researcher's bad output" even though they are span-tree
    siblings.
- **Blast radius is not a flat set** (open question in decisions.md — resolved
  here): each affected node carries a `severity` —
  `FAILED` (the span itself) / `CONTAMINATED` (reached over CALL or a traversed
  HANDOFF) / `AT_RISK` (agent-level neighbor of a contaminated region, reached
  by a non-traversed edge) — plus the edge type(s) that implicated it. The
  report states which claims rest on `agent_source: ANCESTOR` attribution
  (inherited ownership is weaker evidence).
- **Tests:** on the refund trace — CRM failure propagates to writer and final
  answer; policy-search branch stays clean; retry chain reports exhaustion;
  seeded-verdict path localizes a semantic failure on a trace with zero ERROR
  spans (use the real 52-span trace shape for this test).

### M4 — Phase 5: deterministic root-cause localization

**Deliverable:** `src/atlas/analysis/root_cause.py`.

- Candidates = detected failures; a candidate is a *root* when no failure on
  its upstream `CALL`/`HANDOFF` path both precedes it and explains it (same
  agent or an ancestor agent). Roots are ranked by observable graph properties
  only: downstream reach (blast-radius size), retry presence, kind weight
  (exhausted retries > error status > missing output), depth.
- Output `RootCauseReport`: ranked candidates, each with a mandatory
  **evidence chain** (span ids, statuses, edges traversed — plan §22.8), the
  propagation path to the final answer, and retry-waste context. No invented
  confidence percentages in v1; ranking position + evidence *is* the claim
  (plan §13's "dependency-based causal attribution" wording only).
- **Tests:** refund trace → root cause is the CRM tool span, not the writer,
  not the final answer; evidence chain names exact span ids; a clean run
  yields an empty report, not a fabricated one.

### M5 — Phase 6: run store and HTTP API

**Deliverable:** `src/atlas/store.py`, `src/atlas/api/`.

- `RunStore`: file-backed directory (one analyzed run → one JSON document:
  the Run plus the analysis results) with an in-memory index; `POST` re-analyzes
  by rebuilding from the trace. No database in v1 (plan §20).
- FastAPI (`api` optional dependency group) exposing plan §16's surface:
  `POST /runs` (accepts a MASEF trace JSON), `GET /runs`,
  `GET /runs/{id}` (summary), `/graph` (nodes+edges, cytoscape-ready JSON),
  `/failures`, `/diagnosis` (failures + propagation + root cause + retry waste).
  Errors use the same named-path messages ingestion raises.
- **Tests:** `TestClient` end-to-end — POST the refund trace, GET every
  endpoint, assert the diagnosis JSON matches the analysis-layer results
  exactly (the API adds no logic; it serializes).

### M6 — Phase 7: CLI, web UI, optional LLM `ask`

**Deliverables:**

- **CLI** (`src/atlas/cli.py`, entry point `atlas`): `analyze <trace>
  [--format text|json] [--store DIR]`, `serve [--store DIR] [--port]`,
  `ask <question> [--run ID]`. stdlib `argparse` — no CLI framework dep.
- **Web UI** (`src/atlas/api/static/`, served by FastAPI at `/`): three views
  per plan §15 — run list, run detail with the graph (pyvis HTML per ADR-005's
  note that Streamlit renders graphs poorly; no Streamlit), diagnosis panel.
  Read-only, hand-written HTML/JS against the JSON API; no build step, no
  node_modules.
- **LLM layer** (`src/atlas/llm/`) — the thin optional one, exactly the
  architecture the project is pitched with: the LLM is a *query interface*,
  never the analyst. It receives the deterministic tool set
  (`get_run`, `get_failure_chain`, `get_blast_radius`, `get_latency_breakdown`,
  `get_retry_waste`, `get_root_cause`) in a tool-calling loop and answers from
  their outputs only. Key via env var; without a key, `atlas ask` exits with a
  clear message and every other surface is unaffected. Provider SDK is an
  optional dependency group (`llm`); model/provider constants live in one
  module. Anthropic API chosen as the default provider at implementation time
  (consult the claude-api skill then); MASEF's OpenAI judges are unaffected —
  they are a different system.
- **Tests:** CLI output parsing (analyze text/json on the refund trace), API
  smoke through `serve`'s app, ask-layer tool-schema validation with the
  network mocked.

- **Docs pass**: `docs/decisions.md` gains the ADRs forced by M1–M6 (DATA-edge

## 5. Sequence and parallelism

```text
M0 baseline + demo trace
 └─ M1 graph ── M2 retries ── M3 propagation ── M4 root cause   (strict order)
                              (M7 README/LICENSE/CI can start any time after M0)
 M5 store+API  ── starts after M4, freezes response schemas
 └─ M6 CLI+UI+LLM ── starts once M5 schemas are frozen; graph UI needs M1 only
M7 final sweep last
```

Sub-agents are used where the work is genuinely independent (demo-trace
authoring, UI, README/CI) and the core M1→M4 chain is implemented in one
context so the model invariants stay coherent.

## 6. Definition of v1 success

1. Every command in §3 works from a clean clone.
2. `uv run pytest` green, including refund-trace acceptance tests for M1–M4.
3. The repo explains itself: README quickstart → visible diagnosis in under
   two minutes, decisions traceable in `docs/`.
4. Nothing in the tree references private paths, and nothing private is
   committed (`prompt.txt`, `ATLAS.pdf` excluded).
5. The owner reviews the diff, then pushes `main`.
